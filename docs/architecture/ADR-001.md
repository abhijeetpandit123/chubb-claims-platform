# ADR-001: Modular monolith with REST commands and an event port

**Status:** Accepted for assessment scope. **Date:** 2026-11-05.

## Context
The brief asks for a claimant/staff claims platform, expects backend-first delivery, permits Java/Spring Boot, requires Angular, and explicitly leaves REST versus Kafka to the developer. It sets 2–3 hours target / 5 hours maximum, so integration complexity has a high opportunity cost.

## Decision
Use a Spring Boot modular monolith, one H2 database, REST endpoints for interactive UI operations, a domain-owned workflow state machine, and a small event publisher port with a logging implementation. Use one Angular application with role-conditional UI. Do not deploy Kafka in assessment scope.

## Consequences
+ Easy local startup and cohesive transaction boundaries.
+ Readable code and fast test feedback.
+ A replaceable event adapter offers a future integration seam.
- No independently deployed services, event durability, or real async processing.
- H2 persistence is ephemeral; Basic auth is a demo-only shortcut.
- Reporting read model is computed by scanning claims; add indexed projections later.

## Alternatives considered
1. Multiple microservices (claims, identity, reporting): rejected due to operational overhead, distributed consistency and time pressure.
2. Kafka from day one: rejected because no consumer workflow is required to complete core user journey; would demand outbox/idempotency to be responsible.
3. PostgreSQL + Flyway: preferable for real use but omitted for faster one-command demo; high-priority follow-up.
4. Full-blown state pattern: rejected for six deterministic states where aggregate methods are easier to understand and unit test.

## Review trigger
Extract a service when independent scale, team ownership, release cadence or data boundaries demonstrate an actual benefit; adopt Kafka when concrete downstream consumers and reliability requirements exist.
